# AGENTS.md — rules for AI coding agents

These rules apply to any AI coding agent working in this repository (Claude Code, Codex and others). Follow them exactly. If a rule stops you from finishing, stop and tell the owner; do not work around it.

1. **Never touch production — except as rule 19 allows.** Do not run commands, migrations, deploys or queries against production. To learn something from production, use the **owner-runs-query pattern** (Book 2 A24): write a read-only query, give it to the owner, and wait for them to paste back the result. Never ask for production keys. **During the setup phase, rule 19 opens one narrow exception and nothing more; read it before assuming anything here is relaxed. When rule 19 ends, this rule applies in full again.**
2. **Work on a branch, then open a pull request.** Never commit to `main`. Never push to `main`. Never merge your own pull request.
3. **Show evidence before claiming done.** Paste the exact command, its exact output and its exit code. "Should work", "tests pass" or "done" without output is not allowed.
4. **Run one command at a time.** No chaining with `&&`, `;` or `|`. Read each result before running the next.
5. **Never edit guard files.** Do not change, disable, move or work around `.claude/hooks/`, `.claude/settings.json` or `guard/`. If a guard blocks you, stop and tell the owner why. Only a person changes guards. Change `.github/workflows/` only when the owner asks, and never to skip or weaken a check.
6. **Use staging with the test accounts.** Test on staging as **Alice** (owner), **Bob** (outsider — must be refused Alice’s data) and **Carol** (Alice’s team member). Never use real people’s data. See `docs/environments.md`.
7. **Keep secrets out of files and chat.** Never write a key, password or token into any file except an ignored `.env` file, never print one, and never ask the owner to paste one into chat. Only `.env.example` with placeholders is committed.
8. **Say "unverified — reason" when a check could not run.** A check that was blocked, timed out, lacked permission or found zero things to check is **not** a pass. Write `unverified — <reason>` and say how to check it properly.
9. **Stay inside `docs/plan.md`.** Read `docs/plan.md` before starting work in a session, and treat it as the agreed scope. If a request needs something the plan does not list — a new feature, anything from its "deliberately not in the first version" list, a new kind of personal data, a native app, or spending above its budget ceiling — say so **before** writing code: name the part of the plan the request goes past, and ask whether to update the plan or drop the request. Widening the plan is the owner's call. The plan is updated first, then the code.

10. **Local and staging only — except as rule 19 allows.** You have access to local and staging only. You never ask for, read, store or use production keys, passwords or database connections. You never link a command-line tool or connector to the production project. Changes reach production only through a pull request that the owner merges. If a task seems to need production, stop and explain why. This includes the browser: never open, click in, or read a production dashboard for Supabase, Vercel or any other service. **Rule 19 is the only exception, it is temporary, and it is narrower than it looks: it permits production function secrets and nothing else. Schema and code still reach production only through a pull request the owner merges. When rule 19 ends, this rule applies in full again.**
11. **Read the Next.js docs that match the installed version.** Before writing Next.js code, read the version-matched docs in `web/node_modules/next/dist/docs/`.
12. **Long text goes in a file, never inline on the command line.** Write a commit message, pull request description or issue body to a file first, then pass the file: `git commit -F <file>`, `gh pr create --body-file <file>`, `gh issue create --body-file <file>`. Send a long prompt for another tool through standard input, not as an argument. Prose on a command line is fragile — a quote or an apostrophe can split it into something git never sees — and everything that inspects commands, the guard included, reads the prose as if it were the command.
13. **Anything meant to be kept gets saved as a file, in this session.** If you write a procedure, a decision, a plan, or any document meant to outlive the conversation, save it in the project and commit it before the session ends. Chat is not storage: text that only exists in a reply is lost the moment the window closes. If you cannot save it, say plainly **"This is NOT saved yet"** and give the exact step that would save it — the path, and the command.
14. **Check the current state before you state it.** This covers files and claims alike. Before using any file the owner mentions, or any file you remember from earlier in the session, confirm it is on disk and show the command output that proves it — a file can be renamed, moved, never created, or exist only on another branch. The same goes for any claim about how things stand right now: which branch you are on, what is committed, which pull requests are open or merged, whether a workflow ran and what it did, whether a deploy went out, whether a table exists. Run the command and show the output, or say the claim is **unchecked**. Your memory is a record of what was true when you looked, and the owner keeps working between your turns: a merge, a deploy or a run can make it stale within minutes. Stale news delivered confidently is worse than no news, because it sounds like evidence.
15. **Only use what you have confirmed exists, and only report what you have seen.** Four parts, and the last one is how the other three get kept:
    - **Functions, commands and options**: use only ones you have confirmed exist today, either in this project's own code — search for it and show where it is — or in the official documentation, with the link. A remembered API is a guess wearing a uniform.
    - **Numbers**: never present one you did not just calculate or count. Not a row count, a file count, a version, a size or a duration. If you did not count it in this session, say so.
    - **Never "should work"**: not "that should fix it", not "this will work". Run it and paste the exact output and exit code, or say which check would settle it and that it has not been run.
    - **"I don't know"** is a complete answer. Say it plainly, then say how we could find out — the command, the page, the person.
    Before sending any final report, read it back against these four and against rule 14, and fix or mark anything that does not hold.
16. **A follow-up you mention becomes an issue before you finish.** Anything you call "for later", "out of scope", "worth looking at" or "someone should" gets filed as a GitHub issue in the same task, or it does not get mentioned at all. Write each issue's text to a file and pass it with `gh issue create --body-file <file>` (rule 12). Every issue says four things: **what is wrong**, **where it is** — the file, the line, the setting — **why it matters**, and **how we will know it is fixed**, written so somebody else can tell. Before closing a pull request without merging it, file an issue capturing what it was trying to fix, so the reason does not leave with the branch. At the end of the task, list every issue you filed, each with its link. A worry that lives only in a reply is a worry that dies with the reply.
17. **Ask before adding a package.** Before adding any dependency, show the owner its registry page link, its weekly downloads and its maintainer, and **wait for a yes**. Then install it at an exact version and **commit the lockfile in the same change**, so the pull request records precisely what was added. A package is somebody else's code running with your permissions, and the moment to think about that is before it is installed, not after.
18. **Redact captured data before you commit it.** Any data captured from production — a log line, an API response, an error payload, a webhook body, a support example, a test fixture — gets cleaned before it goes into a file, a commit message, an issue or a pull request. Two kinds of value come out, and you look for both every time:
    - **Anything that grants access**: checkout or session IDs, claim keys, reset codes, invite codes, magic-link URLs, tokens, signed URLs, cookie values. Until they expire, these *are* credentials — treat them exactly as rule 7 treats a password.
    - **Anything that identifies a person**: customer or user IDs, email addresses, names, phone numbers, postal addresses, IP addresses, and free text someone typed, which can name a third party who never agreed to anything.
    Replace each one with a clear, consistent placeholder — `CHECKOUT_SESSION_1`, `CUSTOMER_2`, `RESET_CODE_1` — using the same placeholder for the same original throughout, so the example still reads as a coherent story. **Never shorten, mask or star out a real value**: `cs_live_a1b2…`, `sk_…3f9` and `j••••@example.com` are all still the value with a hint attached. Invent a replacement instead of trimming the original.
    Then **list every value you replaced, with its before and after**, in the pull request or the reply, so the owner can check the list is complete instead of taking "redacted" on trust. Where showing the "before" would itself publish the secret, name the value and where it came from rather than printing it, and say that is what you have done. If you captured nothing, say so plainly — an empty list is a complete answer and a better one than a vague reassurance.
    An access-granting value that has already been committed is **leaked, and rotating it is the only fix** (rule 7, and `docs/secrets.md`). Deleting it in a later commit does not un-leak it: anyone who cloned in between still has it. That is the whole reason this happens before the commit and not after.
19. **Production access during setup, and when it ends.** The owner decided on 2026-10-01 to open a narrow, temporary exception to rules 1 and 10. It is narrow on purpose: read it as a list of what is permitted, not as permission to use judgement.
    - **Staging:** you may run `supabase db push`, `supabase functions deploy` and `supabase secrets set` against the **staging** project only.
    - **Production, settings only:** you may set production function secrets (`supabase secrets set` against the production project). **No other production command is allowed** unless the owner adds it to this rule. **There is no guard prompt for this**, so the production log below is the only record that it happened. Schema and code reach production **only** through the pipeline — a pull request the owner merges. Never `db push`, `functions deploy` or a migration against production yourself.
    - **Destructive actions are forbidden everywhere remote**, with no prompt: database reset, `drop`, `truncate`, `delete from`, `functions delete`, `--prune`, deleting a project, a key or a secret. The free plan has no point-in-time restore, so there is nothing to undo with.
    - **Your production token is yours alone:** a Supabase scoped token for the production project, at most 30 days, separate from the pipeline's token, kept only on the owner's machine outside the repository, never printed, never put in a file in the repo, never given to the GitHub Action.
    - **Every production action goes in `evidence/production-log.md` in the same session**: time, who, what, why, result. **A missing entry is a broken rule, not a late one.**
    - **Production email goes only to the test mailbox.**
    - **End trigger:** this rule ends when the first real user signs up, or at launch (Build it 30), whichever comes first. Then the owner revokes the tokens, this rule is removed, and rule 10 applies in full again.

When unsure, stop and ask. Background for people: `README.md`, `docs/architecture.md`, `docs/environments.md`.
